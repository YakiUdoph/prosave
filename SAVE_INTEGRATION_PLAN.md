# SAVE — Functional Integration Plan (Visual Source: SAVE-Original)

This document maps out the integration architecture to connect the approved `SAVE-Original` frontend with the validated X Layer RPC client and the OKX OnchainOS DEX aggregator quotes.

## 1. Security Architecture (Secrets Management)

To ensure that server-side credentials (`OKX_API_KEY`, `OKX_SECRET_KEY`, `OKX_API_PASSPHRASE`) are never exposed in the browser:

```
[ Injected EVM Wallet ]      [ TanStack Start Frontend ]       [ Server Function / API ]       [ OKX OnchainOS ]
       |                                |                                   |                                |
       |-- 1. Connect Address --------->|                                   |                                |
       |-- 2. Read RPC Balances ------->|                                   |                                |
       |                                |-- 3. Fetch Quote (Params) ------->|                                |
       |                                |                                   |-- 4. Sign HMAC-SHA256 -------->|
       |                                |                                   |<-- 5. Return Quote JSON -------|
       |                                |<-- 6. Resolve Quote JSON ---------|                                |
```

- **Client Reads**: Public RPC queries (reading native OKB, WETH, and USDC balances) will occur directly on the client side using `viem` and a public RPC provider (`https://xlayertestrpc.okx.com`).
- **Server API Layer**: All requests to the OKX OnchainOS API will be proxy-routed through a TanStack Start Server Function (`createServerFn`).
- **Signing Key Isolation**: Signature generation (HMAC-SHA256) will run inside the Server Function where `process.env.OKX_SECRET_KEY` is accessible.
- **Transaction Signing**: Private keys from the server will NOT be used for frontend executions. Any transaction execution will be routed to `window.ethereum` for user-approved client-side signature.

## 2. Technical Component Design

### A. Context & State Management (`src/lib/save-context.tsx`)
We will expand the context state variables to track:
- `walletAddress`: string | null
- `chainId`: number | null
- `balances`: Record<string, string> (token balances)
- `parsedIntent`: Extracted intent structured object (target asset, amount, protected tokens)
- `candidatePlans`: Dynamic list of Plan structures generated by the Solver
- `selectedPlan`: "A" | "B" | "C"
- `simulation`: Dynamic simulation details
- `receipt`: Executed action summary values

### B. Wallet & Chain Integration (`src/routes/connect.tsx`)
- Detect EIP-1193 provider (`window.ethereum`).
- Request accounts (`eth_requestAccounts`) via `viem`.
- Check chain ID; if not `1952` (X Layer Testnet), request network switch/add.
- Store address and chain ID in context, then transition automatically to `/scan`.

### C. Portfolio Scanning (`src/routes/scan.tsx` & `src/lib/save-data.ts`)
- Query live native `OKB` and contract `WETH` / `USDC` balances on X Layer Testnet.
- **Demo Data Toggle**: If real balances are 0 (e.g. fresh developer wallet), supplement them with clearly isolated `DEMO DATA` (such as `Token X` and default demo balances) so the hackathon flow remains fully interactive.
- Transition pipeline steps dynamically based on actual resolution of RPC queries.

### D. Intent Parser Engine (`src/routes/intent.tsx`)
- Implement a deterministic parsing routine:
  - Regex match target amount (e.g. `700` or `$700`).
  - Match target token symbol (e.g. `USDC`).
  - Match protected token keyword (e.g. `ETH` or `OKB`).
  - Store parsed targets and constraints to context.

### E. Rescue Solver (`src/lib/solver.ts` [NEW])
- Input: portfolio balances, target amount, protected assets, token prices.
- Algorithmic Routing:
  - **Plan B (Preservation-First)**: Solves the target amount using only unprotected tokens (OKB, TKX). Protects ETH.
  - **Plan A (Max Output)**: Ignores protection constraints, selling ETH/OKB/TKX as needed to achieve maximum output.
  - **Plan C (Conservative)**: Sells a fixed lower ratio of OKB and TKX to minimize slippage, resulting in a shortfall.
- Output: structured actions, target achieved state, and calculated Protection Score.

### F. OKX Proxy Server Functions (`src/lib/okx-server.ts` [NEW])
- Secure functions:
  - `fetchOkxQuote(fromToken, toToken, amount)`: computes headers and fetches live routing swap quotes from OKX.
  - Returns raw gas estimates, slippage, and routing list to the client.

### G. Protection Score Formula
The Protection Score is calculated as:
$$\text{Score} = (\text{Target Satisfaction} \times 40) + (\text{Asset Preservation} \times 30) + (\text{Slippage Safety} \times 15) + (\text{Gas Efficiency} \times 15)$$
- **Target Satisfaction**: 100% if expected output matches or exceeds target, scaled down proportionally if shortfall.
- **Asset Preservation**: 100% if designated protected assets are completely untouched, 0% if any are sold.
- **Slippage Safety**: $100 - (\text{Slippage} \times 100)$ capped at 100.
- **Gas Efficiency**: $100 - (\text{Gas Cost in USD} \times 5)$ capped at 100.

### H. Sandbox execution / Demo Mode (`src/routes/protected.tsx`)
- The "Protect My Portfolio" button will trigger execution in **Demo/Simulation Mode** (generating a mock tx receipt but tracking actual solver outcomes) or **Live Mode** (which prepares transactions for Metamask/OKX Wallet approval).
- We will clearly separate these adapters.
